Snapshot (sha1 prefix): core.py 93f797c, tests 8277c38, cli.py 8449830, install.py df00245, lua 430f485. core.py and the tests changed while I reviewed. Line numbers refer to this snapshot.
Tests: 45 run. One fails when run from a Claude Code shell. All 45 pass after unsetting the inherited Claude identity variables (see #3).

1. HIGH. Verified with live cache evidence and a reproduction. Nested agents take over the parent's pane mapping.
core.py:167-179. A Codex child started from a Claude tool shell, such as a codex companion task or `codex exec`, inherits REX_SERVER, REX_SESSION, and REX_BLOCK. Its locator hook records the parent's pane, and the loop at :173-176 marks the parent's locator ended.
Live evidence in ~/.cache/rex-agents/sessions:
- dx-go-claude-2 (claude f1c6ad66) is ended at block ...0fe6b72cec53, while codex 01a177ed... is live at the same block.
- source-claude-3 (claude db1d9130) shows the same pattern at ...9b11683497f0, with codex 01a177f2... live.
A scratch reproduction gives the same result: claude-parent ended, codex-child live at block:claude.
Effect: the parent loses its pane mapping (`rex: null`, no focus), and the child maps to the parent's pane. Each hook event flips ownership back and forth. I saw this in the cache and in the reproduction. My earlier live `list --json` still showed dx-go-claude-2 mapped, which fits the flapping.
Fix: just before core.py:165, add `if (kind == "codex" and os.environ.get("CLAUDECODE")) or (kind == "claude-code" and os.environ.get("CODEX_THREAD_ID")): return`. This mirrors the conflict rule at core.py:94. Workers stay unaffected because clean_env() strips both variables. Claude nested inside Claude is still not covered.

2. MEDIUM. Verified with a live Rex probe and a reproduction. A closed Rex session blocks a worker name permanently.
core.py:369-376. When an old reservation's session is gone, live_location fails. The fallback `rex block ls -s <session>` at :373 then exits 3 with `Error: session target "session:..." not found`. That CommandError escapes the except block. Every later `launch NAME` fails with that message until someone deletes the file in ~/.cache/rex-agents/launches by hand. The reproduction prints `relaunch blocked: session target "session:gone" not found`.
Fix: wrap :373 in `except CommandError as exc:`. Treat only `session target ... not found` as proof the pane is gone and `continue`. Re-raise anything else, so unreachable hosts still fail closed.

3. MEDIUM. Verified. The test suite fails when an agent runs it.
tests/test_integration.py:418 builds the subprocess env from `dict(os.environ, ...)`. Inside Claude Code, os.environ carries CLAUDECODE and REX_AGENTS_*, so the new rule at core.py:94 raises `rex-agents: Conflicting inherited agent identities; use a clean worker or resume the intended conversation`. Result: 1 of 45 fails here. All 45 pass under `env -u CLAUDECODE -u CLAUDE_CODE_SESSION_ID -u REX_AGENTS_NATIVE_ID -u REX_AGENTS_KIND`.
Fix: `env = dict(clean_env(), CODEX_THREAD_ID="native-one", ...)`, with clean_env imported from rex_agents.core.

4. MEDIUM-LOW. The code path is verified; the race is a hypothesis. Read paths write Reason state as another conversation.
core.py:197-203 runs `reason status --name` under the worker's identity. registry() reaches it through resolve() (core.py:219). So `list`, `doctor`, `focus`, and remote `rex_agents_registry` callers rename local workers. The worker's own hook already does the same rename (core.py:185-189).
Hypothesis: hook() rewrites `dict(old, ...)` (core.py:158, 177-179) and can drop a concurrent `named=True`. A later rename could then overwrite a name the user set.
Fix: in registry(), call `self.me(record["kind"], record["native_id"])` instead of resolve(), and keep naming only in hook(). Discovery becomes read-only, and one cross-identity write path goes away.

5. LOW. The dead parameter is verified; the impact is a hypothesis. Remote launch gets 8 s, not 25 s.
core.py:114 hard-codes `--timeout 8s`. `rex --help` says that flag limits "each connection and nonstreaming request". So `timeout=25` at core.py:331 has no effect, while the remote action may run up to 24 s (lua/rex_agents.lua:18). A slow remote returns a raw rex timeout with no reservation token and no "uncertain" guidance, even though the remote may have created the pane. The remote's own reservation still blocks a duplicate, so the result misleads but does not duplicate.
Fix: in rex(), pass `"--timeout", f"{timeout - 2}s"`. Report remote-launch errors as "outcome uncertain on HOST; inspect before retrying".

6. LOW. Verified by reading the code. `list` fails outright when Rex is unreachable.
core.py:248 calls self.hosts() outside the per-host try. If `rex hosts --json` fails (no reachable server; calls use `--autostart=false`), `list` exits 1 even though the Reason roster at :243 succeeded. `send` still works because it never calls Rex. This matters because SKILL.md tells agents to discover addresses with `list`.
Fix: `try: hosts = self.hosts()` / `except Error as exc: hosts = []; warnings.append(f"Rex hosts unavailable: {exc}")`.
